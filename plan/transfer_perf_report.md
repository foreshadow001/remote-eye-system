# 100G 数据传输性能报告（阶段性）

> 日期: 2026-08-29 · 链路: slave(Win10) → 4090(Ubuntu 24.04) 100G DAC 直连
> 结论先行: **当前瓶颈 = 4090 接收端 /data 写入速度（缓冲写 4.5 GB/s）**，
> 网络与采集端磁盘均有富余。

## 一、系统组成

### 采集端（slave，Windows 10 企业版 LTSC）

| 部件 | 配置 | 实测能力 |
|------|------|------|
| CPU/内存 | 工作站（未饱和，全程 CPU 空闲） | — |
| 数据盘 | Samsung 9100 PRO 4TB ×2（D:/E:, PCIe5 接口） | 读: 单线程 5.46 / 4 线程 **8.14** / 双盘 16 线程 **8.77 GB/s** |

### 处理端（4090 服务器，Ubuntu 24.04 server）

| 部件 | 配置 | 实测能力 |

| 网卡 | LRES1014PF-2QSFP28（双口, 每口独立 100G, 合计 200G, 已核 datasheet） | 双采集机并行合计 113.6 Gbps |

| 接收软件 | `recv_data`（C++）: 每连接一线程, 8MB 对齐缓冲, 缓冲写 + fallocate, `.part` 原子落位 | — |

### 协议

`FILE <rel> <size> <sha|0>\n` + 字节流 → `OK/SKIP/ERR`；每次切换文件一条连接；
已修复头行与数据同包残留丢弃 bug（曾致 short read 4055B，整文件重传自愈）。

## 二、优化迭代史（每轮 250GB 单相机实测）

| # | 版本 | 聚合速率 | 当时瓶颈 |
|---|------|------|------|
| 1 | Python 接收端（recv_data.py） | 1.2 GB/s | **Python GIL 单核 100%** |
| 2 | C++ 接收端 + 用户态读发 sender | 2.0 GB/s | 发送端读/发串行 |
| 3 | + TransmitFile（内核读发重叠） | 3.5-3.8 GB/s | **接收端写盘（当前）** |
| 4 | + O_DIRECT（含 fallocate 预分配） | 2.45 GB/s | XFS 未写 extent 慢速转换（回退） |
| 5 | + O_DIRECT（去掉 fallocate） | 2.45 GB/s | md0+xfs 直写路径仍慢（回退，留 `--direct` 开关） |

流数扫描（C++ 缓冲写版）: 2/3/4/6/8 流全部 3.5-3.8 GB/s —— 与流数无关的总量封顶。
单流 TCP 实测上限 ~1.9 GB/s（无竞争时），2 流即打满 3.8。

## 三、排除项（全部实测验证）

| 假设 | 验证方法 | 结果 |
|------|------|------|
| Windows Defender 实时扫描 | 关闭实时防护 A/B 重测 | 无差异（4.29 vs 4.50） |
| 采集端磁盘慢 | C# 多线程本地读 | 8+ GB/s，充裕 |
| CPU（任一端） | 传输中 top/tasklist 采样 | 全程无饱和核 |
| 网卡/线缆/MTU | iperf3 与巨帧 ping | 57Gbps 单机 / 113.6G 双机，充裕 |
| Python 测量假象 | Python 多线程读封顶 4.5 → C# 重测 8+ | 早前"平台期"部分为 GIL 假象 |

## 四、当前瓶颈分析

数据链（各环节实测上限）:

```
采集端磁盘读 8.1 GB/s → 100G 网络 7.1 GB/s → 4090 接收写 /data 4.5 GB/s(缓冲) / 5.8(直写)
                                            ↑ 瓶颈: 传输实测 3.8 ≈ 缓冲写上限的 85%
```

关键观察:
1. **RAID0 上缓冲写 4.5 ≈ 单盘水平** —— 两块 8TB 组 RAID0 后写吞吐没有翻倍,
   说明瓶颈在 xfs 单写路径/md 层, 而非盘本身（直写能到 5.8）
2. O_DIRECT 反而更慢（2.45）: XFS 对直写的 extent 处理 + md 层屏障, 即使去掉
   fallocate 也无法恢复 —— 该路线已放弃
3. 3.8/4.5 ≈ 85% 的效率损失来自 TCP 栈 + 应用层（recv→write 拷贝）

## 五、下一步候选方案（供审核）

| 方案 | 预期 | 改动量 | 风险 |
|------|------|------|------|
| **A. 拆 RAID, 双盘独立挂载 `/data1` `/data2`, 接收端按文件轮盘分流** | **~9 GB/s**（每盘独立 4.5, 文件级并行天然分流） | 接收端加输出根轮转; 重挂载 | 需清空现有 /data 或迁移; 目录分散 |
| B. 保持 RAID, xfs 挂载/分配参数调优 (allocsize/swalloc 等) | 4.5→5? 不确定 | 小 | 收益不明 |
| C. 接收端 io_uring / 多线程分段写单文件 | 提升单文件写并行度 | 中, Linux 专有 | 复杂度高 |
| D. 维持现状 3.8 GB/s | — | 无 | 单参与者 2.5TB≈11min, 双机并行 5TB≈11min |

**推荐 A**: 与"文件级并发"的现有架构最契合（每文件一连接一写流, 只需决定落盘根）,
预期把接收端上限从 4.5 抬到 ~9, 传输随之到 **6-7 GB/s**, 5TB 双机并行 ≈ 6-7 分钟。

## 六、复现性与最终基线 (2026-08-29 补记)

同一配置 (RAID0 + 4 流 + TransmitFile + 缓冲写) 的实测方差带:
- **冷态 (可复现规划基线): 3.4-3.8 GB/s**
- 热态上沿 (发送端待机缓存有余温 + RAID0 刚重建): 4.2-4.4 GB/s — 不可持续, 不作规划依据
- 尾部单流 (并行收尾) 最高 1.56 GB/s, 印证并发读交错是单盘主要惩罚

规划口径: 单盘 1.25TB ≈ 5.8 min; 四盘串行 5TB ≈ 23 min; 运行时不带参数
(workers 默认 4)。追高需 io_uring / OS 缓存策略级改造, 投入产出低, 暂缓。

## 七、当前部署参数快照

- slave: `send_slave.exe`（TransmitFile, workers=4 默认, CHUNK 8MB, SNDBUF 32MB）
- 4090: `transfer/recv_data`（缓冲写, 每连接线程, 8MB 对齐缓冲; `--direct` 备用开关）
- 网络: 10.10.2.0/24 (slave), MTU 9000 两端一致; ufw 按接口放行
- 已知收尾事项: 清理测试 junction (P000W2/3/6, P000D1/D2, P000OD2/OD4, P000OE2)
  与 4090 `/data/P000W* /data/P000D* /data/P000OD* /data/P000OE*` 测试目录
